# Loop Playbook — Long-Term Lens daily improvement

This file is the loop's operating manual. The scheduler holds only a pointer to it.
The loop improves by editing this file (via cron.update on the scheduler body when
the pointer itself must change, and by committing playbook edits with the run's
other changes). Every rule here was earned by a real incident; the history is in
docs/loop-log.md.

## Risk tiering (explicit)
- This is a static personal site: no backend, no user data beyond the visitor's
  own localStorage, no payments. Blast radius of a bad push: a broken static page
  for visitors until revert.
- Therefore: direct-to-main shipping with the three gates below is the chosen
  risk posture — deliberate, not lazy. This posture does NOT transfer to any
  multi-user or stateful system.

## Rollback
- `git revert <sha>` (or `git reset --hard <last-good>` on the local tree followed
  by a normal push — the PAT helper pushes the tree, so a local revert + push
  is the rollback), push via the PAT helper, then GATE 2 (CI green) and GATE 3
  (live version.txt matches the reverted version). One paragraph, no improvisation.

## Secrets and shipping path
- Pushing uses `~/workspace/skills/github-pat/bin/push.py` with a GitHub PAT
  (repo + workflow scopes). No secret values live in this repo, in docs, in logs,
  or in chat — ever. Report only whether the push worked, never the token.
- If pushes start failing with 401/403: the token was revoked or expired. The loop
  cannot self-repair this — it needs Kevin to re-issue. Report it plainly and stop
  attempting pushes; keep doing read-only work (tests, audits) in the meantime.

## Testing (every run)
0. RECONCILE THE TREE: `git fetch origin main`, then compare the working tree to
   origin/main before touching anything. Pushes go out via the GitHub API, which
   can leave the local clone behind the remote with shipped changes sitting
   uncommitted (2026-10-22: v4.4.4 was live and byte-identical to the tree, but
   the tree was dirty and HEAD was one commit behind). Verify against the
   DEPLOYED bundle (curl + byte-compare), then reset to origin/main. Never build
   on a tree whose relation to the shipped state is unknown.
1. `npm test` first (full suite, real exit code).
2. Live-test the DEPLOYED site (cache-busted): every one of the five tabs renders real content, Profile shows the saved result immediately (new visitors land on Profile; saved profiles open on Ideas), Check-ins badge behavior, add idea → seal thesis (read-only after sealing) → check-in form closes → trend "Find companies" add-as-idea flow, Ideas filter, Learn jump link to Accounts. Desktop width in browser; phone = static CSS review + Kevin's iPhone is the final visual gate — say so honestly. Safari-compat inspection each run.
3. Edge cases (pick 3-4): rapid clicking, refresh mid-flow, 40+ char names, emoji names, cleared localStorage, legacy migration, export contents, keyboard tab order.
4. README check: describes the actual UI (five tabs, Trends inside Ideas, Accounts inside Learn, no More menu)? The badge and per-suite split are pinned by `tests/run.js` — the suite fails if they drift from runtime counts; TESTING.md's count paragraph must be hand-updated on count changes and the runner catches a missed one.
5. NEW-FEATURE RULE (2026-10-18): every new user-facing feature ships with its own deep-test round — jsdom click-through of the feature, live verification on the deployed URL, and assertions pinning its behavior. Features are not "done" when coded; they're done when deep-tested.
6. CONTENT RULE (2026-10-18): any new factual content (quotes, figures, claims) must cite a primary source. Misattributed or unverifiable content is a release-blocker. For quotes: verify against the primary source text, not quote-aggregator sites.
7. HERMETIC-SUITE RULE (2026-10-18): no test may depend on timer/event-loop luck. If a test fails intermittently, the product code gets a guard (like the fetch guard) or the test gets deterministic control — never a retry loop.
8. VISUAL-QA FALLBACK (2026-10-18): if the browser task flakes, use the VM's Chromium at /opt/meta-chromium/chrome over CDP (remote-debugging-port) with jsdom-serialized snapshots (inline styles.css, file:// URL) for screenshots. Never let a flaked visual check go unverified. (2026-10-21 extension: Chrome 152 blocks localhost http:// navigations via CDP with ERR_BLOCKED_BY_LOCAL_NETWORK_ACCESS_CHECKS, even as the launch URL — the local-http-server route is dead on this build. Working recipe: curl the deployed files, diff byte-identical against local, load the bundle via file:// as Chrome's initial launch URL (never Page.navigate), fresh --user-data-dir per run, drive with Node's global WebSocket — no constructor options, the second arg is the protocols slot. Full recipe in docs/TESTING.md. Never `pkill -f` a pattern that appears in your own command line — use the `pgrep -f "[p]attern"` bracket trick.) (2026-10-23: codified as `tests/browser-pass.js`, run via `npm run browser-pass <deployed-dir>` — self-contained, 12 checks + zero-console-error assertion, kills Chrome on exit. Run it against the curled deployed bundle after the byte-identity diff.) (2026-10-29: if the harness times out on the debugger page, check Chrome's stderr FIRST — a startup policy error ("Hatch WebGL domain policy is required for browser startup", reproduced with and without --no-sandbox) is an environment blocker, not a product failure. Do not chase a product fix for it; verify via the live-browser fallback instead, and record which route verified what.)
9. DEBLOAT CHECK (2026-10-18): each run, report app.js/styles.css/index.html line counts and scan for dead functions (defined once, never referenced) and dead CSS classes. Growth must be feature-driven; cut or justify anything else. (2026-10-19 extension: also flag CSS custom properties used via var() but never defined, and write-only module state (assigned, never read) — both shipped real issues the function/class scan missed. 2026-10-21 note: the test-enforced CSS token scan is authoritative — hand-rolled shell greps for var()/write-only state are redundant and bug-prone; do not duplicate them.)
10. GREP-PIN SMELL (2026-10-21): any test that only greps source for a string is a candidate for a behavioral replacement. Safety mechanisms (self-heal guard, sealed read-only, UTC ban) deserve click-through tests, not string matches.
11. COPY RULES ARE TEST-ENFORCED (2026-10-23): user-facing copy rules (plain language, no work-words) must be pinned by assertions where feasible, not just audited by eye — a prompt label violated the plain-language rule for months while audits read past it. When an audit finds a copy violation, add the assertion that would have caught it (e.g. the no-shouty-labels test).
12. DOCS WITH NUMBERS ARE MACHINE-CHECKED (2026-10-23): any doc that states a number (README badge, TESTING.md counts) must be verified by a test. tests/run.js pins the README badge and split against live suite counts — hand-updated numbers are a smell; when the runner flags drift, fix the docs, never silence the runner.
13. PIN NON-DEFAULT PATHS (2026-10-25): the 2026-10-25 audit's findings were all the same shape — a pure function tested only on its default path (`reviewAtOf` without 1/12, `spotPriceOf` but not the seal handler's empty-log guard, `normalizeIdea`'s review-history sanitization but not its status/name/`reviewMonths` fields). When a helper has branches, every branch gets an assertion, and every call site with its own guard gets a click-through test — the helper's test does not cover the call site.
14. NEGATIVE CONTROLS ARE MANDATORY (2026-10-25): every regression test written for a fixed bug must be verified to FAIL on the unfixed code before shipping, and the loop-log entry must record that the negative control was run. A test never seen failing is a test never proven to guard anything.
15. DEFERRED-ITEM TRIAGE (2026-10-25): each adversarial audit re-triages the deferred list with an explicit disposition per item — fixed, re-deferred with reason, or escalated to Kevin. No deferred item sits unexamined for more than two audit cycles.
16. SUITE BUDGET (2026-10-25): the full suite must stay fast enough to run twice per push cycle. If wall time exceeds ~60s, profile and split before adding more — a slow gate gets skipped, and a skipped gate is no gate.
17. NEGATIVE-CONTROL RUNS MUST COMPLETE (2026-10-30): a control run that aborts early proves nothing about the tests after the abort — a null deref in test code (not product code) silently skipped half the guards in the 2026-10-30 control run. Guard every test DOM lookup that a missing fix could null out, and confirm both suites reported before calling the control done.
18. FOCUS TESTS MUST MIRROR REAL BROWSERS (2026-10-30): jsdom `.click()` never moves focus, and `focus()` on an element inside a hidden screen is a no-op (same as browsers) — so a focus test that doesn't first focus what a real click would have focused, or that never navigates to the screen, passes vacuously. Navigate first, focus first, then assert.

## Shipping gates (all must pass, in order, no exceptions)
- GATE 1 — LOCAL TESTS BEFORE PUSH: immediately before pushing, run `npm test` on the exact tree being pushed and confirm exit code 0. The suite run at session start does NOT cover edits made during the session — re-run after the last code change, every time. If red: fix, re-run, then push. Never push a red tree. (Why the explicit gate: pushing via the GitHub API bypasses any local pre-push hook, so the loop's own discipline is the only front gate. 2026-10-21: Kevin asked for this gate by name.)
- Five-place version bump (package.json, APP_VERSION, version.txt, footer, ?v=). Test-only changes may skip the bump.
- Push via PAT push.py (has workflow scope).
- GATE 2 — CI GREEN: after pushing, poll the GitHub Actions runs for the pushed SHA until the `tests` workflow concludes. It must be green before the run is called done. CI is the independent backstop: `.github/workflows/test.yml` runs `npm ci` + `npm test` on Node 24 for every push to main (and every PR). On CI failure: download the logs via the API, read the real error (never guess), fix locally, re-run GATE 1, push again. If a poll is interrupted (restart, timeout), query the run status via the API — never re-push to "retry" a poll.
- GATE 3 — LIVE VERIFY: confirm the deployed version.txt matches the pushed version, then live-verify the fixes on the DEPLOYED URL (cache-busted). Iterate until right — never ask Kevin to verify.
